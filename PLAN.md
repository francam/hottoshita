# Hottoshita – iPad App Plan

## Overview
A daily wellness check-in app designed for elderly users. After answering a short series of questions, the app generates a readable report and emails it to a pre-configured trusted contact. Available in English and Japanese.

---

## Target User
- Elderly individuals using an iPad or iPhone
- Large text, Dynamic Type support, generous touch targets
- Minimal navigation, guided linear flow

---

## Screens

### 1. Onboarding (first launch only)
- Enter the user's own name
- Enter trusted contact name and email
- All three fields required before "Get Started"
- Saved to UserDefaults via `@AppStorage`

### 2. Home Screen
- Personalised time-aware greeting: "Good morning, John!" (localized)
- Current date
- Large "Start Today's Check-in" button
- History button (top left) — opens past check-ins
- Settings gear (top right)
- "Already submitted today" banner replaces start button if check-in was already done today; small escape hatch to submit again
- ⚠️ **TODO:** History and Settings buttons need to be larger and easier to tap for elderly users; consider grouping them closer together or moving to a more prominent location

### 3. Check-in Flow (one question per screen)
Questions presented in order with progress bar and Back/Cancel navigation:

1. **Sleep** – How was your sleep? (Slept deeply / Slept OK / Barely slept / Didn't sleep)
2. **Feeling** – How are you feeling now? (multi-select grid: Good, Tired, Dizzy, Heavy, Anxious, Happy, Sad, Calm)
3. **Blood Pressure** – Can you take your blood pressure? (Yes / No)
   - If Yes → numeric input screen (systolic / diastolic)

Each screen:
- One large question + SF Symbol icon
- Big tappable answer buttons with teal highlight on selection
- Slide + fade transition between steps

### 4. Summary Screen
- Review all answers before sending
- "Send Report" (saves entry + opens Mail), "Done", and "Start Over" buttons

### 5. Email Report
- Opens iOS Mail compose sheet (`MFMailComposeViewController`)
- Subject and body fully localized (English + Japanese)
- Pre-filled: To (trusted contact), Subject ("Daily Check-in – date"), Body

**Email body format:**
```
Tuesday, June 2, 2026

Hello Sarah,

Here is John's wellness check-in for today:

Sleep: Slept deeply
Feeling: Calm, Happy
Blood Pressure: 120/80 mmHg

--
Sent via Hottoshita
```

### 6. History Screen
- List of all past check-ins in reverse chronological order
- Each row shows date + sleep / feeling / blood pressure summary
- Empty state if no entries yet

### 7. Settings Screen
- "About You" section: edit user's own name
- "Trusted Contact" section: edit contact name and email, or fill both via "Choose from Contacts"

### 8. Contacts Integration
- "Choose from Contacts" buttons in Onboarding (contact step) and Settings
- Uses `CNContactPickerViewController` (`Utilities/ContactPickerView.swift`) — runs out-of-process, so **no Contacts permission or Info.plist key is needed** and the user never sees a permission prompt
- Contacts without an email address are greyed out; contacts with several emails drill in so the user picks one
- Picker fills the name + email fields; the user can still edit before continuing
- Presented via UIKit from an invisible host controller (embedding the picker directly in a SwiftUI sheet can render blank)
- `--debug-contact-picker` launch arg (DEBUG only) jumps to the contact step and auto-opens the picker, for manual testing

## Data Model

```swift
enum SleepRating: String, CaseIterable, Codable {
    case deeply = "Slept deeply"
    case ok = "Slept OK"
    case barely = "Barely slept"
    case none = "Didn't sleep"
}

struct BloodPressure: Codable {
    var systolic: String
    var diastolic: String
}

struct CheckInAnswers: Codable, Identifiable {
    var id: UUID
    var sleep: SleepRating
    var feelings: [String]          // ordered, from feelingOptions
    var tookBloodPressure: Bool
    var bloodPressure: BloodPressure
    var date: Date
}

// UserDefaults keys (via @AppStorage)
// "userName"     — the user's own name
// "contactName"  — trusted contact's name
// "contactEmail" — trusted contact's email
```

`CheckInStore` — `@MainActor ObservableObject` persists entries as JSON in the app's Documents directory. Accepts an injectable `fileURL` for unit testing.

- **Language:** Swift 5.9
- **UI Framework:** SwiftUI
- **Email:** MessageUI (`MFMailComposeViewController` wrapped in `UIViewControllerRepresentable`)

- **Localization:** `Localizable.strings` in `en.lproj` and `ja.lproj`; all views use `LocalizedStringKey` / `String(localized:)`
- **Project generation:** xcodegen (`project.yml`)

### Roadmap — future versions (reorganised 2026-07-15)

#### v1.5 — quality-of-life around contacts

- [ ] **Self contact entry sync — know who the user is, with locale-aware naming.** Prefill the user's own name at onboarding instead of asking for it cold. iOS has no public API for the "me" card (`unifiedMeContact` is macOS-only), so the flow is: on the name step, offer "This is me" via the permissionless `CNContactPickerViewController` (same approach as the trusted-contact picker); if the user is not the device owner, they tap "I'm someone else" and today's text field remains as the manual fallback.
  **Naming rule:** picking a contact card gives us `givenName`/`familyName` components — store both, and address the user per locale: **Japanese uses the family name for 〜さん** (田中さん), **English uses the given name** ("Good morning, Miguel"). Touches the home greeting, the splash "Hi %@!", and the report intro (report probably wants the full formatted name via `CNContactFormatter`). Manual single-field entry stays verbatim in both languages (whatever they typed is what we call them).
- [ ] **Multiple trusted contacts.** Replace the single `contactName`/`contactEmail` pair with a list. Onboarding keeps collecting exactly one contact (setup stays simple); Settings' Trusted Contact section becomes an add/remove list, each row fillable via the contact picker. `MFMailComposeViewController.setToRecipients` already accepts multiple addresses, so one email goes to everyone — decide To vs BCC (family usually fine with To; BCC if contacts shouldn't see each other). Wrinkles: the report greeting "Hello %@," needs a multi-name form (or a generic 皆様/"Hello,"), and the summary's "Will be sent to: %@" should list or count recipients. Migrate the existing two UserDefaults keys into the list on first launch.

#### v2 — Liquid Glass + Apple Intelligence

- [ ] **Liquid Glass design** (prototyped 2026-07-15 on the `liquid-glass` branch, commit d9c454b, pushed to origin). Verdict from the experiment: looks great — glass choice tiles with accent-tinted selected states, glass chrome/action buttons, frosted summary cards; compiled first try against the beta SDK. Decision: **keep iOS 16 support** — do NOT raise the deployment target for visual flair. Implementation therefore needs availability branching, best centralised so UI code isn't duplicated: small helper modifiers (e.g. `glassOrBorderedProminent()`, `glassOrBordered()`, and a `tileBackground(selected:)` that picks `glassEffect` vs the solid fill) that branch on `if #available(iOS 26.0, *)` in ONE place each. Before merging: re-check contrast of unselected glass tiles for the elderly audience (they're softer than the current solid cards) and view on a real device. The branch is a clean 5-file diff — rebase it when v2 starts rather than letting it rot.
- [ ] **Apple Intelligence: optional dictated memos, summarised on-device.** New optional step in the check-in flow: a big microphone button lets the user dictate a free-form memo (system keyboard dictation, or the Speech framework for a guided elderly-friendly UI). Summarise it on-device with the Foundation Models framework and include the summary in the email. Must degrade gracefully: on devices without Apple Intelligence, include the raw transcribed memo instead. Memo is skippable in one tap.
- [ ] **Apple Intelligence: weekly summaries for the contact.** Once a week, aggregate the week's check-ins (sleep pattern, recurring feelings, blood-pressure readings and their trend, missed days) and have the on-device Foundation Models turn them into a short, warm narrative the trusted contact(s) can read at a glance — e.g. "Miguel slept well most of the week, felt tired on Thursday, blood pressure stayed steady." Surfaced as a "Send weekly summary" prompt (Home banner when a week completes, and/or a button in History); sent through the same Mail flow, and respects the multiple-contacts list once v1.5 lands. Fallbacks by design: without Apple Intelligence hardware, send a template-based digest computed from the same aggregates (no model needed); generation stays fully on-device either way, consistent with PRIVACY.md.
- [ ] **Calendar sync — surface important events in the report.** Read the user's calendar with EventKit (needs calendar permission + purpose string; iOS 17+ read-only `NSCalendarsFullAccessUsageDescription` / `.fullAccess` request). Include in the emailed report anything notable the person attended today or has coming up (e.g. doctor's appointment) — likely a keyword/calendar-selection filter ("Doctor", "病院", or user-picked calendars in Settings) so routine events don't clutter the email. Show the matched events on the Summary screen before sending so the user sees exactly what the contact will read.
